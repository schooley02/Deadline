# Art Style — Sprites, Categories, Base States

## Style
Pixel art / cartoonish. Playful, slightly eerie (graveyard setting) but never grim. Suitable for a younger audience.

**LOCKED 2026-07-21** (DECISIONS.md): pixel art is confirmed as the permanent style — all future assets match the existing 64×64 zombies. Sprite visibility over the background is handled by contrast (dark, low-detail silhouette background layers; bright saturated sprites — see VISUAL_DESIGN_PLAN.md V1), not by changing sprite style.

## AI Asset Pipeline (decided 2026-07-21)
- **Base sprite generation:** Retro Diffusion (true grid-aligned pixel art; use existing assets/renders as style reference).
- **Animation / rotations:** PixelLab (text-prompted cycles, 4/8-direction rotations, Aseprite extension).
- **Format:** raster PNG only — the pipeline is PNG sprites positioned by DOM/CSS; no vector sprites. SVG is used only for scene silhouette props (V1).
- Background is layered; camera tilt rejected — never rotate pixel sprites. **2026-10-27: the layers no longer move with the time slider (ground, hills and clouds locked; the cloud drift and sprite animations follow the drag instead, see UI_UX.md).** Old rates, for history: **(V1 live-tuning, 2026-07-21): ground −22% (fastest — the original "ground fixed" call was reversed), clouds −18%, silhouettes −7%.** **Stars (2026-11-01, Jeremy):** 14 pixel twinkling stars in their own layer `.scene-stars` (index.html, css/gameCanvas.css) just above the sky gradient (z -4, so the moon and clouds pass in front): 10 small 2x2px dots + 4 larger "+" stars (2px centre, 2px arm each side via box-shadow, no blur), cream #f6f0d4 / #fffdf2, all in the top ~35% and left of the moon. The blink is STEPPED (`steps(1)` per keyframe, two variants `star-twinkle-a/b`), each star has its own `--star-dur` (2.8-5.8s) and negative `--star-delay`. Not a slider scrub target (keeps twinkling while you drag). Static (opacity .8) under `.fx-reduced`, `.fx-off` and prefers-reduced-motion. Purely decorative; a future sky-weather hook (V7) could react to run state. Tune by editing the inline `left/top/--star-*` on the spans. **Clouds (2026-10-27):** PixelLab pixel art, 2x like the church: `Assets/scene/clouds-tile.png` (625x72; sources `Assets/scene/_source/cloud-a.png`, `cloud-d.png`), 3 muted lavender-grey colours (#8c89a8 / #5a5878 / #3d3a5c), dark underside (no light bottom row), no outline. Brief that worked: "pixel art night cloud, isolated, transparent background, puffy rounded top, flatter bottom, moonlit from the upper right, 4-5 colour palette, no anti-aliasing".

## Canvas & Sprite Dimensions (from base view notes)
- Game canvas reference: **720 × 368**
- Character sprite sizing reference: **1290 × 720** scene basis. Zombie sprites are **64×64** source pixels (sub-tasks render at 64×64; tasks/habits scale up). Scale only by CSS with `image-rendering: pixelated`.

### Light technique: see-through glow (Jeremy 2026-11-17) -- use for every light source in village art (2026-11-18: ONLY actual fixtures -- lamps, floodlights, lit signs, candles; never lit windows or doors)
Light that shines past the building's edge must NOT stop dead at the silhouette. Where a beam, wash or bloom crosses open air (transparent pixels), keep drawing it as PARTLY TRANSPARENT pixels in the light's colour; where it crosses opaque art, brighten those pixels instead. The game draws the PNGs with alpha, so the glow shows over whatever sits behind the building.
- **Recipe (code, done last, after the colour pass):** for each pixel inside the light's shape compute a strength k (falls off with distance from the source and toward the shape's edges, e.g. `k = k0 * (1-d/R)^1.5 * (1-(dx/half)^2)`); opaque pixel -> blend toward the light colour by k; transparent pixel -> set the light colour with alpha `~255*k*0.9`, capped around 150-160 so it never reads as a solid shape; skip tiny alphas (< 7).
- **Colours:** warm lamps / pendants (255,214,150); cool floodlights (240,246,255); the Police spotlight (255,244,214).
- **Used on:** Gym T5 pendant light (cone over the open bay), Gym T5 floodlights (bloom + wash past the right wall edge), Police station T5 roof spotlight (round bloom into the sky + light on the roof and wire beside it; `defense_t5.png` and `police_t5_final_160x160.png`, 2026-11-17 -- phones need an sw bump to see it).
- **Check on a phone:** the glow mixes with the sky/ground behind the village, so judge it in the game, not only on the flat preview colour.

### PixelLab API workflow (learned on the Gym, 2026-11-14) -- use for every Village 2.0 building
- **Access:** Jeremy's API key lives only in the Claude session workspace (never in the repo); `api.pixellab.ai` is on the allowed-domains list. Check

- **What worked:** `generate-image-v2` (Pro, 15 gen / 4 images) with Jeremy's pick as reference + a flat-colour layout guide; `resize` (1 gen) to make a building
  BIGGER -- the generators copy the reference's pixel size, so a bigger canvas alone does not enlarge the building; `inpaint-v3` (Pro, 10 gen per image) with
  a white-on-black mask for every tier edit and fix (people, equipment, defenses, flag). Run 2 seeds and let Jeremy pick.
- **What failed:** `create-image-bitforge` with an upscaled init (turned clapboard into brick); bitforge inpaint (painted blank wall); thin things from

  fix instead.
- **Box seams:** an inpaint patch only redraws inside its rectangle; if the area around it was tone-shifted in code, the patch edge shows as a box. So do
  brightness/colour passes ONLY at the very end of a tier, never between edits. A per-plank-row luminance pull evens siding if boxes appear.
- **Clean-ups to expect:** inpaint over sky fills the gaps with dark navy (erase dark pixels above the roof line); objects cut at the mask edge (redo with a
  mask that leaves room); straight unoutlined cut edges (add a dark outline in code).

  `gallery:<id>` to replace; free). API generations also appear in his PixelLab history, failed ones included -- tell him which one is final.
